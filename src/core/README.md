# core

What the project's things *do*: infrastructure logic and the building blocks of the project, including anything that owns resources.

Names here start with `core_`. May use: `data/`, `util/` and the top of `src`.

## Modules

- `collision.h`: `core_collision_resolve_pair` (two spheres) and `core_collision_resolve_walls` (one sphere against a `data_bounds` box), worked out in place on a `core_spheres_view` by index. Pure physics: no window, time step or globals; rgba is never read. Mass is the circle's area, and pi cancels, so r * r is used.
- `grid.h`: `core_grid`, grid space partitioning for sphere pairs. `core_grid_resolve_pairs` bins the spheres with a counting sort (each cell becomes a contiguous slice of indices) and resolves every overlapping pair exactly once, in the first cell the two share. `core_grid_sort_spheres` reorders all six sphere arrays by each center's cell (stable counting sort, through a scratch block), so spheres near each other on screen are near each other in memory. Buffers are kept between steps and only grow; `core_grid_size_for` picks columns and rows for a sphere count, and `core_grid_resize` applies them.
- `spawn.h`: `core_spawn_lattice` fills n² spheres on an even n × n lattice over the bounds: a random radius from 0.5 to 1 times `core_spawn_lattice_max_radius` (0.4 of the smaller cell side, so neighbors start apart; the grid is sized from it), a random direction at 0.5 to 2 cells per second, random RGB with alpha 255.
- `sprite_batch.h`: `core_sprite_batch` (raii; `NO_COPY`, `NO_MOVE`, `NO_RETURN`: only the simulation owns one), the vertex buffers for drawing every sphere as one textured quad: xy, colors, uv and u32 indices as separate arrays (SoA, as `SDL_RenderGeometryRaw` takes them). `prepare` rebuilds everything after the count or order changes; `update` writes only the 8 position floats per sphere each frame. `core_sprite_circle_alpha` gives the anti-aliased circle texture's pixels.
- `window.h`: the backend-neutral window. `core_window_subsystem()` (SDL's global init), `core_window` (raii, its implementation hidden in a `memory_block`, `NO_COPY` and `NO_MOVE`), events as `data_input_event`, a nanosecond clock, and drawing: clear, a sprite batch, a filled triangle, debug text (8 px glyphs, scaled), present. Two implementations, one per build:
  - `window_mock.c` (with `window_mock.h`): headless, used by every local build and every test runner. A fake 60 Hz clock, a 64-event queue tests push to, a quit after `core_window_mock_set_frame_limit` frames (600 by default), and per-frame draw statistics.
  - `window_sdl.c`: SDL3, only in CI release builds (`-DBOUNCING2D_SDL=ON`). WorkshopC doesn't check it, since SDL's headers never exist locally.
- `physics.h`: whole-array steps: `core_physics_move` (x += vx * dt) and `core_physics_resolve_walls` (every sphere against the box, inlined per-axis logic so it vectorizes). A frame: move, then grid pairs, then walls.
- `spheres.h`: `core_spheres`, the simulation's spheres as a structure of arrays (x, y, vx, vy, radius, rgba) in one `memory_block`, each array a multiple of 16 elements long. `core_spheres_get_view` gives every array at once for system loops (copy the pointers into `restrict` locals); storage only: values are set from outside through the view, and `make` and `core_spheres_resize` (the only way to change the count) leave every sphere zeroed. Views carry the spheres' generation: `core_spheres_view_is_current` is false after a resize, move or destroy, and every function taking a view asserts it, so Debug builds catch a stale view at its first use. A view's type decides whether it writes (`core_spheres_view`) or not (`core_spheres_const_view`), not the const on its pointer.
